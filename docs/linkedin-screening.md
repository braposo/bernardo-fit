# LinkedIn Engineering Manager discovery

The published `fit-analysis-settings.linkedinScreening` document controls daily discovery. Policy v2 searches public LinkedIn results for **Engineering Manager** across the **United Kingdom**. It does not apply LinkedIn's remote filter: remote work is a preference during card screening, and a city or unknown arrangement is not grounds for exclusion. The published candidate preferences say remote-first is a strong preference, not a requirement, and the published constraints record no remote-only requirement. The separate full-description assessment and its published minimum admission score still decide whether a fetched job is saved.

Each configured search covers the newest up to `maxSearchResults` unique posting IDs (initially 80). `searchPageSize` (40) is only a request hint; LinkedIn may return a different number of cards. The worker deduplicates IDs and advances offsets by the actual number of cards returned. Reaching the configured result limit is a successful completion of the daily scope and advances the checkpoint. The separate `maxSearchPages` value (10 initially) is a safety ceiling: if it is reached before the result limit or an explicit end-of-results page, coverage is incomplete and the checkpoint does not advance. HTTP errors and repeated pages before the configured result limit are also incomplete. This bounded newest-results policy does not promise coverage of every LinkedIn posting. Reports state the per-search cap and whether the configured scope completed.

There is no persisted continuation offset. Each daily run starts at offset zero and applies the rolling window since the last completed search, falling back to the last successful run and then a seven-day bootstrap window. Older pending cards remain stored and are reported as backlog, but only cards that reappear in the current bounded result set are screened or enriched. Completing the configured scope advances the success checkpoint even when uncertain cards or older pending cards remain deferred; real screening, description, or ingestion failures still make the run incomplete.

Jev evaluates the public card against the published candidate profile. `investigate` means positive evidence that it is a relevant Engineering Manager opportunity; the full description is fetched only when that answer's probability reaches `relevanceProbability` (initially 0.8). A confident `mismatch` skips. Uncertain cards are deferred and reported for later screening. The card is untrusted input, and neither title ambiguity nor missing salary or working-arrangement detail proves a mismatch. The full-description admission process remains separate from this preliminary gate.

## Rollout and pause

The canonical Studio field is `lib/sanity/studio/linkedinScreening.ts`. Copy it to the standalone `studio-fit-app/schemaTypes/linkedinScreening.ts` and apply `migration/linkedin-screening-studio.patch` to wire the Analysis settings tab. The standalone Studio is a separate repository and must be updated through its own review process. Keep the published policy disabled while deploying the compatible app/worker and Studio. Then run `node --env-file=.env.local scripts/migrate-linkedin-discovery-v2.mjs` to dry-run, followed by `--apply --worker-compatible`; this revision-guarded patch adds `maxSearchResults:80` without altering the published enabled state or unrelated drafts. The old worker tolerates the additive value, while the new task refuses to search if the policy is enabled before this field has been published. Enable only after the deployment and disabled-policy check.

Deploy and verify the v2-compatible production worker **before** publishing v2 settings. The currently deployed v1 worker does not understand `policyVersion` or `enabled`; publishing v2 early could let it keep using the old search and pacing behavior. Then dry-run `node --env-file=.env.local scripts/migrate-linkedin-discovery-v2.mjs`. After checking the published revision and rollout, run it with `--apply --worker-compatible`. The script patches only the published LinkedIn policy paths under a revision guard, does not publish drafts or overwrite unrelated Analysis settings, and sets `enabled:false`. Review a disabled daily run; enable discovery in Studio only after production behavior is validated. `enabled:false` is the v2 operator switch: the compatible task exits before public requests. The daily dispatcher itself may still invoke the task. A disabled scheduled run consumes that day's global idempotency key. For validation after enabling on the same day, use a direct manual trigger with a fresh identity or wait for the next scheduled day.

The older additive seed remains at `scripts/seed-linkedin-settings.mjs`. An apply now requires `--worker-compatible`, because a missing settings object would receive disabled v2 defaults. The validator can read published v1 settings for migration compatibility; the v2 discovery task refuses v1 before public requests until the migration is published. Existing v1 fields for the single-page result limit, mismatch threshold, and fixed request pauses remain in Sanity for audit but are hidden in Studio and ignored by v2. V2 keeps `requestTimeoutSeconds` and native Trigger `retry`; Trigger owns HTTP retry delays and any `Retry-After` handling. No unconditional delay is configured between successful requests.

The pinned Trigger SDK exposes `schedules.deactivate(scheduleId)` for Trigger-managed schedules, but this workflow's daily dispatcher is a Sanity scheduled function, not an in-repo Trigger schedule. No schedule was changed during this migration. To pause the currently deployed v1 behavior before the compatible worker is live, pause that Sanity dispatcher through its supported operator controls; the v2 Sanity switch cannot affect old worker code.
